\## Onboarding a Repository When you connect a new repository, the system runs an onboarding flow that sets up the documentation structure before any drafts are generated. Onboarding creates a skeleton of documentation nodes that maps to the sections in your chosen deployment target. ### How Onboarding Works 1. The system proposes a documentation skeleton — a tree of pages and sections — based on your doc type and deployment target. 2. You review the proposed skeleton, optionally excluding pages you do not want to track. 3. You confirm the skeleton. The system creates the corresponding nodes in Notion (if configured) and stubs out the pages in your deployment target. ### Reviewing the Proposed Skeleton The skeleton proposal screen shows every page the system plans to create, grouped by top-level page and sub-section. Each page has a checkbox — deselect any page you want to exclude from tracking. Excluded pages are not created in Notion or your deployment target and will not receive generated drafts. After you finish reviewing, select \*\*Confirm\*\* to save the skeleton and begin onboarding. ### Onboarding Statuses While onboarding runs, the repository settings panel shows the current status. Onboarding moves through the following states: - \*\*Awaiting skeleton\*\* — the system is waiting for you to confirm the proposed skeleton. - \*\*Awaiting confirmation\*\* — the skeleton has been submitted and is being processed. - \*\*Complete\*\* — onboarding finished successfully. The repository is ready to generate drafts. - \*\*Failed\*\* — onboarding encountered an error. Check the error message and retry. ### Bootstrap Mode After the skeleton is confirmed, the system enters \*\*bootstrap mode\*\* to generate initial documentation for your repository. Bootstrap mode processes your existing codebase and creates a first set of drafts for every confirmed section. The bootstrap progress view shows the status of each node as the agent works through them. A progress indicator tracks how many sections are complete out of the total. Once all sections are processed, bootstrap is marked as done and you can navigate directly to the activity feed to review the generated drafts. If the system detects that a previous bootstrap attempt failed, it surfaces the failure so you can retry from the repository settings panel. ### Bootstrap vs. Backfill The system distinguishes between two bootstrap modes: - \*\*Bootstrap\*\* — runs when the repository has no prior documentation history. The agent generates drafts for all confirmed sections from scratch. - \*\*Backfill\*\* — runs when the repository has existing commit history that the agent has not yet processed. The agent works through past commits to bring your documentation up to date. The mode is determined automatically based on your repository's state. ### Rediscovering an Existing Structure If your deployment target already contains documentation, you can run a rediscovery instead of building a skeleton from scratch. Rediscovery reads your existing content structure — for example, the pages listed in a Mintlify \`docs.json\` — and proposes it as the skeleton. You review and confirm the imported structure the same way you would a new skeleton.
