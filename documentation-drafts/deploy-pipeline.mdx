\## The Deployment Pipeline When you deploy a draft, the system queues a background job that converts your content and pushes it to the configured deployment target. Understanding how the pipeline works helps you diagnose issues and retry failed deployments. ### What Happens When You Deploy 1. The system enqueues a deploy job containing the draft ID and the target configuration. 2. A background worker picks up the job and fetches the latest approved content. 3. The content is converted from Markdown to the format required by the target (for example, MDX for Mintlify or rich text blocks for Notion). 4. The worker pushes the converted content to the target platform and records the result. 5. If the push succeeds, the draft status moves to \*\*Deployed\*\*. If it fails, the status moves to \*\*Failed\*\* and the error is recorded. ### Retrying a Failed Deployment If a draft reaches the \*\*Failed\*\* status: 1. Check the deployment error displayed in the editor panel for details about what went wrong. 2. Verify that your deployment target configuration (credentials, repository, branch) is correct in your repository settings. 3. Select \*\*Deploy\*\* again to requeue the job. ### Markdown to HTML Conversion Before content is pushed to certain targets, the system converts Markdown to HTML using a configurable converter. The converter preserves headings, paragraphs, bold and italic text, inline code, fenced code blocks, and bulleted lists. ### Force Redeploy If a section is already in the \*\*Deployed\*\* state and you want to push updated content — for example after making manual edits — you can trigger a force redeploy. The system treats this the same as a new deployment and pushes the current content to the target.
