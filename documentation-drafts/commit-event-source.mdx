\## How Syscribe Processes Commits Syscribe generates documentation drafts in response to \*\*commit events\*\* — records of code changes that the agent processes. Understanding the source of a commit event helps you interpret the activity feed and the history log. ### Commit Event Sources Every commit event has a \*\*source\*\* that identifies where the trigger came from: - \*\*Pull request\*\* — the standard source. A commit event is created when a pull request is opened or updated in your connected GitHub repository. - \*\*Bootstrap\*\* — the commit event was created by the bootstrap process. These events represent the initial documentation generation run when you first onboard a repository, not a real code change. - \*\*Backfill\*\* — the commit event was created by a backfill run. Backfill events process historical commits to bring your documentation up to date. You can identify bootstrap and backfill events in the activity feed by their badge — bootstrap events display a \*\*bootstrap badge\*\* instead of a commit SHA pill. ### Commit Event Statuses Each commit event moves through the following statuses as Syscribe processes it: | Status | Meaning | |---|---| | \*\*Pending\*\* | The event has been received and is queued for processing. | | \*\*Processing\*\* | The agent is actively generating drafts for this event. | | \*\*Complete\*\* | All drafts have been generated and are ready for review. | | \*\*Failed\*\* | The agent encountered an error processing this event. | ### Parsed Data When Syscribe processes a commit event, it parses the associated pull request or commit to extract the code changes. This parsed data is stored alongside the event and used by the agent when generating drafts. You do not interact with this data directly — it informs the content the agent produces.
